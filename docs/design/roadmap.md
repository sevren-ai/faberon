# Faberon: Roadmap

**Status:** living document. Features planned for the near future, plus open questions that affect that work. Updated whenever plans or decisions change, by humans or by agents (see `AGENTS.md`). Stable architecture lives in [design.md](design.md). Speculative ideas and deferred options live in [future.md](future.md). This doc is not a history: git records what shipped and why.

**Current focus:** 
* v0.3.0 (chat + local executor): [v0.3.0.md](v0.3.0.md).
* v0.3.1 (drafter + campaign succession): [v0.3.1.md](v0.3.1.md).
* v0.4.0 (security): [v0.4.0.md](v0.4.0.md).

## Phases

A version is a milestone release, not the whole roadmap. Each phase becomes its own version with its own design doc when its design review happens.

- **v0.3.0: chat + local executor.** Pi extension on the login node: `inject_idea`, live campaign status streamed from the ledger. Adds an `experiment.designing` event so the proposer's LLM wait does not read like a hang, and a `faberon` CLI for shell operations. Human-injected ideas are advisory-only for now. The CLI also submits human-authored plans. Also a local executor behind the existing `submit`/`status`/`cancel` interface: run the training script as a subprocess on the machine hosting Faberon. Serves users without a Slurm cluster (e.g. a provisioned A100/H100 box, or a workstation). Covers the output-file convention the metric is parsed from, restart-safe submission idempotency without an external job registry (pid records on disk), walltime enforcement without Slurm, an env switch next to `create_app_slurm()`, and a workstation runbook.
- **v0.3.1: drafter + campaign succession.** The drafter: conversational intake in the chat interface that interviews the human and drafts a plan, submitted through the same create path as a hand-written one. A finished campaign can be followed up: mechanically (same plan, fresh budget, no LLM) or drafted in the chat interface when the plan should change. `POST /v0/campaigns` accepts an optional `predecessor`; the new campaign starts from the predecessor's best kept commit and the ledger records the succession. Also live progress in `CampaignInfo` (experiments done, GPU-hours burned, baseline to current best), derived from the ledger.
- **v0.4.0: security.** Contain the three attack surfaces: LLM-written code (container sandboxing, AST policy), API token (structured `command`, token hardening), and local executor (resource limits, confined working directory). See [v0.4.0.md](v0.4.0.md).
- **v0.5.0: scale + portable operation.** Concurrency-limited queue for ablations (git worktrees arrive here, one linked working tree per job on its own commit, shared venv and data); real budget enforcement if not already covered by the gate work; epilog webhook once egress is verified; restart drills as routine. Scheduler-specific knobs (`--partition`, QoS) land here too, behind the executor interface now that two executors exist. Also the single-machine lifecycle: `faberon serve` becomes `faberon start` (background-by-default, with `faberon stop` and a foreground escape hatch), and it bootstraps and restarts Postgres (the open question below). Also contract tooling: with the v0 API settled after v0.3.0, generate the chat interface's TypeScript types from the brain's OpenAPI spec (replacing the hand-maintained `types.ts`) and commit JSON Schema / OpenAPI goldens so contract drift fails CI.
- **v0.6.0: research quality.** Judgment quality (robust confidence measure, eval-suite non-regression backpressure, constraint-aware gates); living notes file; plan stop-conditions honored end-to-end (LLM-parsed, not stand-in). The ledger records parent and new sha so the lineage tree is reconstructable.

## Open Questions

Questions that affect near-term work. Broader deferred ideas belong in [future.md](future.md).

- Database schema versioning: today the schema is created idempotently (`CREATE TABLE IF NOT EXISTS`) and never migrated, so upgrading between versions requires recreating the database and losing its data. Once Faberon has users who cannot do that, adopt a real mechanism: a `schema_version` table, ordered migration steps, a startup check that refuses to run against an unexpected version, and a migration test that upgrades an old schema and asserts the new code works against it. The open question is timing: which release is the first one that must not break an existing database.
- Multi-file repo edits: the proposer is limited to replacing one Python file, which the plan names in its required `target_file` field. General repo editing lands with the scale work in v0.5.0, alongside worktrees. That design review settles commit scoping: plan-listed paths vs. an agent-decided commit tool vs. `add -A` with an ignore-file convention for run outputs.
- Compute-node to login-node HTTP egress (gates the epilog webhook).
- Single-machine lifecycle mechanics: v0.5.0 ships `faberon start` / `faberon stop` (background-by-default, foreground escape hatch) and Postgres bootstrap, one lifecycle for both processes. The open questions are mechanical: how `faberon start` detaches (double-fork vs. supervisor), where logs and pid records live (a state dir, following the local executor's on-disk pid pattern), and who restarts each process after a reboot (systemd units where the user controls them, `faberon start` ensuring Postgres otherwise). Settles at the v0.4.0 design review; until then the workstation runbook documents the manual `scripts/db/` scripts and the README's tmux/screen advice.
- Executor-interface pressure: scheduler-specific knobs (`--partition`, QoS) belong in v0.5.0 and must stay behind the executor interface now that v0.3.0 adds a second executor. The v0.5.0 design review decides what, if anything, enters the shared `SubmitRequest` vs. stays adapter config. `--time` walltime is already pulled forward to v0.2.0.
- Constraint-aware judgment: today judgment scores one metric movement with a confidence measure. Constraint-driven search (e.g. edge models that must fit a size or memory budget) needs a hard gate distinct from the scored objective: keep only if the metric moves AND the run satisfies a budget. Settles where the constraint lives (plan schema field vs. judgment step) and whether it is a per-run gate or a campaign-level rule.
- Frontier exploration: keeping several branch tips alive per campaign instead of one best (idea described in future.md). Settles at the v0.5.0 design review, where worktrees arrive: the pruning rule (when a branch dies: dominated, budget share, age), how the proposer chooses which branch to extend (exploit the leader vs explore the rest), and what `campaign.ended` reports when several branches survive.
