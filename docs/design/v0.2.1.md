# Design Document: Faberon v0.2.1 (robustness)

**Status:** current WIP (design review last updated 2026-09-23).
This doc describes what v0.2.1 should ship and is frozen afterwards.

## Goal

Patch release. The first real v0.2.0 campaign exposed a set of operability defects: two campaigns can corrupt one repo, a crashed or hung campaign is indistinguishable from a slow one, a proposer failure can kill a campaign, and the control plane can be hard to stop and unsafe to restart. v0.2.1 fixes those, without changing the campaign loop's scope.

Still tested against Karpathy's [autoresearch](https://github.com/karpathy/autoresearch) (5-minute `train.py`, `val_bpb` metric).

## In scope

- **One active campaign per repo.** The campaign loop assumes sequential checkouts, but nothing enforces it: two campaigns started against the same experiment repo interleave commits, resulting in corrupt git history. `POST /v0/campaigns` rejects a new campaign when its target repo already has an active campaign (a campaign row with no `campaign.ended` event). The campaigns table gains the repo path so the check is possible.
- **Informative commit messages.** Today every experiment commit is titled `experiment N`, where `N` is a per-loop counter that resets renumber, so the git log does not identify experiments and discards make the numbering jump. The commit message becomes a one-line summary of the actual change (from the proposer's rationale), prefixed with the campaign's experiment index so the log stays interpretable across discards: `exp 3: extend LR warmdown 0.5 -> 0.7`.
- **Proposer call timeout.** The propose step is one blocking LLM call with no timeout. A hung model wedges the campaign: the loop never returns to the top, so `cancel` (checked only at the loop top) is never seen, and a restart replays straight back into the same hung call. The proposer call gets a timeout; on expiry the step fails, the loop regains control, and cancel or a retry can proceed.
- **Proposer failure is not fatal.** The proposer's output validator retries a no-op or invalid replacement, and when the retries run out Pydantic AI raises `UnexpectedModelBehavior`, which today kills the workflow (this exact error ended a real campaign with no terminal event). A model that proposes a no-op or invalid edit is a recoverable condition, not a fatal one: the loop catches the proposer failure, records it, and either retries the proposal or counts the iteration and moves on. A campaign must not die because the model had a bad turn.
- **A constantly-failing proposer ends the campaign.** The failure path skips `experiments_done`, so a proposer that fails on every call (dead endpoint, output the validator always rejects, every call hanging to timeout) spins the loop forever: no terminal event, no GPU spend, nothing but `experiment.propose_failed` entries. Cancel still works (the failure path returns to the loop top), but nothing bounds the campaign on its own. A fixed consecutive-failure ceiling, reset on any successful proposal, ends the campaign with the `error` stop reason.
- **SSE shutdown.** Open SSE ledger tails block uvicorn's graceful shutdown: it waits for connections to close, SSE connections never close on their own, and SIGINT is absorbed. Stopping the control plane then needs SIGKILL. Streaming responses must close on the shutdown signal (or uvicorn must bound the wait) so the process stops cleanly.
- **Crashed campaigns leave a terminal event.** An unhandled exception in the loop (for example a failed `git` call in `tree.py`) kills the workflow with no `campaign.ended`, so the ledger shows a campaign frozen mid-run and a later cancel can never land. The loop wraps its body so an unhandled exception records a terminal `campaign.ended` event (a new `StopReason` such as `error`) before the workflow fails. Cancel and restart then always have a defined end state to act on.
- **Campaign status.** Today nothing distinguishes a running campaign from a hung or dead one: the ledger goes quiet in all three cases, and the workflow's real state (SUCCESS/ERROR) lives in DBOS, which no route exposes. `GET /v0/campaigns/{id}` gains a `status` derived from the ledger and the DBOS workflow state: `active` (events, no `campaign.ended`), `ended` (with its stop reason), or `error` (no `campaign.ended` and the DBOS workflow is in ERROR). `GET /v0/campaigns` returns the same status per campaign.
- **Recovering a crashed campaign.** A campaign in ERROR holds its research (proposals, judgments, best metric, kept shas) in the ledger, but the dead workflow cannot reliably resume in place: re-running it re-enters the step that crashed. Recovery is by re-seeding, not resume: read the best metric and head sha from the ledger and start a fresh campaign with that baseline. This is the supported path; true in-place resume depends on the proposer-failure item above removing the crash in the first place.
- **Start without replaying campaigns.** DBOS resumes PENDING workflows on launch. If a recovered workflow is what destabilizes the cluster, startup becomes a crash loop: recover, resubmit, kill, repeat. The control plane gets a start mode (an env flag such as `FABERON_NO_RECOVER`) that serves the API but does not resume workflows, so the operator can inspect and cancel campaigns one by one before letting any run again. Per-campaign resume then happens through an explicit call, not automatically at boot.
- **Schema additions in the quarantined module:** an `error` value in `StopReason` for crashed campaigns, and a `campaign.crashed` event type that carries the exception detail.
- Runbook updated for the new start mode and the crashed-campaign recovery path.

## Out of scope

Planned for later releases: see [roadmap.md](roadmap.md). Speculative ideas: see [future.md](future.md).

- Console, drafter, idea injection, `faberon` CLI: v0.3.0.
- Parallel experiments (worktrees, DBOS queue): v0.4.0.
- Judgment quality (confidence measure, non-regression, constraint gates), the notes file, approval gates: v0.5.0.

## v0.2.1 limitations

- **In-place resume of a crashed campaign is not supported.** Recovery is re-seeding from the ledger. A dead workflow stays dead.
- **Crash-cause diagnosis is manual.** The status field says a campaign is in `error`; finding why still means reading the DBOS error.
- **No database schema migration.** The `campaigns` table gains a `repo_path` column, but Faberon has no migration mechanism yet. Upgrading to v0.2.1 requires recreating the database (`scripts/db/drop-faberon-db.sh`, then `scripts/db/create-faberon-db.sh`); existing campaign and ledger data is discarded. Proper schema versioning is planned for a later release (see [roadmap.md](roadmap.md)).

## Exit test

- Start a campaign. Starting a second campaign on the same repo is rejected with a clear error.
- Stop the control plane with an SSE stream attached: it shuts down cleanly, no SIGKILL.
- Restart the control plane with the no-recover flag: the API serves, no workflow resumes, and each campaign can be resumed explicitly.
- The proposer timeout, proposer-failure recovery, crashed-campaign terminal event, and campaign status are exercised in the test suite (a hung model and a forced exception are not reproducible in a manual run), not in this on-cluster exit test.
