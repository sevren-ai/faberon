# Design Document: Faberon v0.1.0 (skeleton)

**Status:** current WIP (design reviewed 2026-09-02). 
This doc describes what v0.1.0 should ship and is frozen afterwards.

## Goal

One thin path through every tier, proving durability end-to-end:

hand-POSTed plan → validation → DBOS workflow submits stock `train.py` (Karpathy's [autoresearch](https://github.com/karpathy/autoresearch): fixed 5-minute budget, `val_bpb` metric) via real `sbatch` → durable `sacct` poll → parse metric → one keep/discard judgment → events in Postgres, streamed over `GET /events`.

## In scope

- Monorepo scaffold: `uv` project, `packages/control-plane`, docs
- Quarantined schema module: event record + plan models
- Executor interface (`submit`/`status`/`cancel`) with fake-subprocess shim for tests
- Real Slurm adapter (local subprocess on the login node)
- Event ledger: Postgres
- DBOS workflow: submit → poll → judge, one concurrent job
- FastAPI surface: `POST /campaigns`, `GET /events`, minimal run status
- Postgres setup scripts: native on dev machines, no-sudo install on login nodes

## Out of scope

Planned for later releases: see [roadmap.md](roadmap.md). Speculative ideas: see [future.md](future.md).

## v0.1.0 stand-ins

Some pieces ship as minimal stand-ins, replaced by the full design later:

- **Judgment.** The v0.1.0 judge is a fixed rule: keep if the metric improved over the baseline (lower is better, matching `val_bpb`), else discard. It has no confidence measure and no constraints. The full judgment design (robust confidence measure, eval-suite non-regression backpressure, constraint-aware gates) is future work.
- **Poll interval.** The v0.1.0 poll interval is a fixed value passed by the caller. Adaptive `sacct` polling based on queue-wait estimates is future work.


## Exit test

Kill the control-plane process mid-run while a job is on the cluster. Restart. The workflow resumes, the job is not resubmitted, the poll picks up, and the result is judged and logged exactly once.
