# Design Document: Faberon v0.3.0 (chat + local executor)

**Status:** current WIP (design review last updated 2026-10-06).
This doc describes what v0.3.0 should ship and is frozen afterwards.

## Goal

A human no longer needs `curl` to run or watch a campaign. A Pi extension on the login node injects ideas, shows campaign status, and cancels campaigns. A `faberon` CLI covers the same operations from a shell, including submitting plans. A local executor also lets Faberon run where there is no Slurm cluster: the training script runs as a subprocess on the machine hosting Faberon (a workstation, or a provisioned A100/H100 box).

Still tested against Karpathy's [autoresearch](https://github.com/karpathy/autoresearch) (5-minute `train.py`, `val_bpb` metric).

## In scope

- **Chat package.** `packages/chat/`, a Pi extension in TypeScript, sibling to `packages/brain/`. It talks to the brain over the v0 HTTP contract with the bearer token from the environment. The extension exposes each v0 operation as a Pi tool (typed parameters, validated against the contract) plus a matching slash command; live status builds on that tool layer. It reasons conversationally, but every write is a human-initiated API call. The chat interface proposes; the brain decides. Faberon Chat versions independently of the brain and ships its first release as `chat-v0.1.0`, speaking API v0; it is distributed as a Pi package from the repo (`pi install git:github.com/sevren-ai/faberon@chat-v0.1.0`), so users do not clone or build it. It is developed and tested against Pi `1.0.0` (`@earendil-works/pi-coding-agent`); the extension API we use (`registerTool`, `registerCommand`, `ctx.ui` widgets, packages) is 1.0.0 surface, and we pin to `^1.0.0` while Pi settles after its 1.0 refactor.
- **Idea injection.** `POST /v0/campaigns/{id}/ideas` wraps `DBOS.send`: the idea lands in the ledger as `idea.injected` and the proposer weighs it at its next decision boundary. Advisory only in this release: the proposer reads ideas as context, nothing forces execution. The imperative config flag arrives with the approval-gate work.
- **Live status.** The chat interface streams `GET /v0/campaigns/{id}/events` (SSE) and renders the ledger live: proposals, completions, judgments, budget burn.
- **`experiment.designing` event.** The proposer's LLM call takes minutes and the ledger is silent meanwhile, which reads like a hang when watching the raw stream. The campaign loop records `experiment.designing` before the LLM call and `experiment.proposed` after, so the stream shows the wait.
- **`faberon` CLI.** Typer, same type-annotation style as the FastAPI/Pydantic stack. Flat verbs: `faberon serve`, `faberon create`, `faberon list`, `faberon show <id>`, `faberon events <id>`, `faberon cancel <id>`. The CLI reads the token and base URL from the environment (`FABERON_API_TOKEN`, `FABERON_API_URL`). The CLI is a thin client of the v0 write surface with no LLM in it.
- **Schema additions in the quarantined module:** `experiment.designing` and `idea.injected` event types.
- **Campaign creation from the CLI.** A `create` command submits a human-authored plan (file or flags) through `POST /v0/campaigns`. This closes the gap where plan submission alone still needed `curl`.
- **Local executor.** A new executor behind the existing `submit`/`status`/`cancel` interface runs the training script as a subprocess on the machine hosting Faberon. It serves users without a Slurm cluster. It covers the output-file convention the metric is parsed from, restart-safe submission idempotency without an external job registry (pid records on disk), and walltime enforcement without Slurm. An env switch selects it next to `create_app_slurm()`.
- Every job's stdout/stderr log is written to `{repo}/.faberon/{job_id}.out`, derived from the campaign's target repo (not from global config), and the brain parses the metric from that file. The plan names only the metric; there is no separate metric command. The local executor's state dir holds only its pid records, never logs.
- **Workstation runbook.** A runbook for running Faberon on a single machine with the local executor. Postgres setup and restart stay manual (the `scripts/db/` scripts) until the lifecycle question settles; see [roadmap.md](roadmap.md).
- Faberon Chat and CLI documented in the README and the cluster runbook.

## Out of scope

Planned for later releases: see [roadmap.md](roadmap.md). Speculative ideas: see [future.md](future.md).

- Additional security.
- Parallel experiments (worktrees, DBOS queue)
- Judgment quality (confidence measure, non-regression, constraint gates), the notes file, approval gates and the `POST /v0/approvals/{id}` write path. Faberon Chat in this release has no approvals to act on, because no actions are gated yet.

## v0.3.0 limitations

- **Hand-maintained contract types.** The chat interface's `types.ts` mirrors the Pydantic models by hand while the v0 contract is still moving. Once it settles, the types are generated from the brain's OpenAPI spec (see [roadmap.md](roadmap.md)).
- **Idea timing.** An injected idea is visible to the proposer at its next decision boundary. An idea injected mid-experiment does not interrupt the in-flight job.
- **Chat errors.** The chat interface surfaces API errors as-is. No retry or offline queue.
- **No database schema migration.** The `events` table's `justification` column is renamed to `reason`, and the `campaigns` table's `command` column is folded into the plan. Faberon has no migration mechanism yet. Upgrading to v0.3.0 requires recreating the database (`scripts/db/drop-faberon-db.sh`, then `scripts/db/create-faberon-db.sh`); existing campaign and ledger data is discarded. Proper schema versioning is planned for a later release (see [roadmap.md](roadmap.md)).
- **Local executor has no isolation or queueing.** Runs execute as subprocesses on the host machine, one at a time. A crashed or untracked process is cleaned up through its pid record; there is no cgroup, container, or node-level isolation, and no GPU allocation logic. Parallel local runs will be implemented later.

## Exit test

On the login node, with Faberon running:

- Watch the campaign live through the CLI: `experiment.designing` appears while the proposer thinks, proposals, completions, and judgments stream in, budget burn updates.
- Inject an idea mid-campaign. It lands in the ledger as `idea.injected` and the next proposal reflects it.
- Cancel the campaign from the chat interface. The loop stops at its next decision boundary with `campaign.ended` naming `cancelled`.
- The same four operations work through the `faberon` CLI with no `curl` and no hand-written URLs.
- Submit a hand-written plan through the CLI's create command. The campaign starts; no `curl` involved.
- On a workstation with no Slurm, select the local executor through the env switch and run a short campaign end to end. The training script runs as a local subprocess, the metric is parsed from its output file, judgments and budget burn land in the ledger.
- With the local executor selected, kill the Faberon process while an experiment runs and restart it. The workflow resumes, the in-flight run is detected through its pid record, and no duplicate experiment is submitted.
- With the local executor selected, give an experiment a walltime it will exceed. The executor kills the subprocess at the limit and the campaign records the outcome like a Slurm timeout.
