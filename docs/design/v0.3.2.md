# Design Document: Faberon v0.3.2 (drafter)

**Status:** current WIP (design review last updated 2026-10-06).
This doc describes what v0.3.2 should ship and is frozen afterwards.

## Goal

A human can draft a research plan conversationally instead of writing JSON by hand. A drafter mode in the chat interface interviews the human and produces a plan for review and submit. 

A finished campaign can get a successor more easily. A successor starts a new campaign from the predecessor's best kept commit keeping to the same research plan but with a fresh budget. `list` and `show` also show live campaign progress (experiments done, GPU-hours burned, baseline to current best) derived from the ledger.

Still tested against Karpathy's [autoresearch](https://github.com/karpathy/autoresearch) (5-minute `train.py`, `val_bpb` metric).

## In scope

- **Drafter.** A conversational intake mode, hosted in the chat interface, that interviews the human and drafts a `ResearchPlan`. It is a mode layered on the chat interface's tool layer, not a standalone feature: it ends by submitting the reviewed plan, though only upon explicit human confirmation. The drafter has no autonomous authority: its only output is a plan the human reviews and submits through `POST /v0/campaigns`. Validation in the brain stays the sole acceptance gate.
- **Succession from the best kept commit.** `POST /v0/campaigns/{id}/successor` creates a campaign's successor. The brain derives the predecessor's best kept commit from its ledger (the `sha` of the last `experiment.judged` with `judgment=keep`) and its best kept metric, rejects a predecessor that is still active, and starts the new campaign's working tree at that commit. The new campaign's `campaign.created` payload records `predecessor: {campaign_id, sha}`.
- **Succession commands.** A `successor` command (CLI, and a chat action on a finished campaign) creates the successor using `POST /v0/campaigns/{id}/successor` with fresh `budget_gpu_hours` and `max_experiments` given explicitly. The brain derives the predecessor's plan with those limits and the baseline seeded from the predecessor's best kept metric. This is the one-step form of the v0.2.1 re-seed recovery.
- **Repo state in the campaign record.** The campaign record gains `branch` and `start_sha` next to `repo_path`: the working branch the campaign commits on and the commit it starts from. Both are exposed through `CampaignInfo` like the other campaign attributes. The `campaigns` table gains two columns. The schema still has no migration mechanism, so recreating databases between versions stays the rule until the schema-versioning question on the roadmap settles.
- **Campaign working branch.** Every campaign commits on a named working branch, recorded as `branch`. The default is a fresh branch per campaign, `faberon/<short-id>` (the campaign ID's first 8 hex characters), created at the repo's current HEAD for a root campaign and at the succession sha for a successor. A campaign never resets a branch it does not own, and the repo's other branches never move on their own. Both creation paths accept an optional `branch` to override the default. A user-named branch that does not exist is created at the campaign's start commit. One that already exists is adopted as-is by a root campaign (its tip becomes `start_sha`); a successor rejects it with guidance unless it already points at the succession sha, since adopting it otherwise would strand commits.
- **Clean-tree checks.** Creation rejects, with guidance, when the repo has no commits, when the working tree has uncommitted changes to tracked files, or when it has untracked files that git's exclude files do not cover (`.gitignore`, `.git/info/exclude`, `core.excludesFile`).
- **Experiment tags.** Every experiment commit is tagged `faberon/<campaign_id>/exp-<N>` right after it is committed, kept or discarded. No recorded commit is ever left dangling: discards stay reachable through their tag, and the loop only ever resets its own working branch across its own tagged commits.
- **Drafter-assisted succession.** When the plan should change (new goal, a pivot informed by what was tried), the drafter starts from the finished campaign instead of a blank interview: it pre-fills the plan, summarizes what was tried from the event stream, and iterates with the human before submit. The reviewed plan goes through `POST /v0/campaigns` like a hand-written one; validation in the brain stays the sole acceptance gate.
- **Live progress in `CampaignInfo`.** The campaign detail response carries progress derived from the ledger: experiments done, GPU-hours burned, baseline to current best. `list`/`show` and the chat interface render campaign progress without a separate events read.
- **Per-campaign GPU count.** The plan gains a `gpus` field (default 1): each campaign declares how many GPUs one job requests, passed to Slurm as `--gres=gpu:N`. The `slurm_gpus` deployment setting becomes the per-job cap: campaign creation rejects a plan above it, and the executor clamps at submit time as defense in depth (the walltime pattern from v0.2.0). GPU-hour accounting, both budget enforcement and live progress, multiplies each job's sacct elapsed time by the GPU count the job was actually submitted with. The `experiment.completed` payload records the effective values (`gpus`, `walltime`), so accounting uses the submitted count and progress stays correct even if plans differ.

## Out of scope

Planned for later releases: see [roadmap.md](roadmap.md). Speculative ideas: see [future.md](future.md).

- Parallel experiments (worktrees, DBOS queue)
- Judgment quality (confidence measure, non-regression, constraint gates), the notes file, approval gates and the `POST /v0/approvals/{id}` write path. Faberon Chat in this release has no approvals to act on, because no actions are gated yet.

## v0.3.2 limitations

- **Drafter plan quality.** The drafter drafts; the human reviews and edits before submitting. No autonomous plan acceptance.
- **A successor is a new campaign.** It does not continue the old workflow, budget, or experiment count. It is a fresh campaign whose plan and starting commit derive from its predecessor. Recovery of a still-pending workflow stays with `POST /v0/campaigns/{id}/resume` and is unchanged.
- **Succession needs explicit limits.** The successor command does not guess a budget: `budget_gpu_hours` and `max_experiments` are required inputs, since the predecessor's were consumed. The drafter-assisted path proposes them in conversation instead.

## Exit test

On the login node, with Faberon running:

- Draft a plan through the chat interface's drafter, review it, submit it. The campaign starts.
- Let a campaign end, then create a successor with explicit budget and experiment limits. The successor starts from the predecessor's best kept commit, its `campaign.created` event names the predecessor, and its first judgment compares against the seeded baseline.
- Draft a successor through the drafter instead. The plan arrives pre-filled, the summary matches the ledger, and the human approves before submitting.
- `faberon list` and `faberon show <id>` render live progress: experiments done, GPU-hours burned, baseline to current best, without reading the event stream.
