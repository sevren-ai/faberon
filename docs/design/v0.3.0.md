# Design Document: Faberon v0.3.0 (console + local executor)

**Status:** current WIP (design review last updated 2026-10-05).
This doc describes what v0.3.0 should ship and is frozen afterwards.

## Goal

A human no longer needs `curl` to run or watch a campaign. A Pi extension on the login node hosts the drafter (conversational intake that produces a plan), injects ideas, shows campaign status, and cancels campaigns. A `faberon` CLI covers the same operations from a shell, including submitting plans. A finished campaign can be followed up: a new campaign succeeds it from its best kept commit, either mechanically (same plan, fresh budget, no LLM) or drafted through the console when the plan should change. A local executor also lets Faberon run where there is no Slurm cluster: the training script runs as a subprocess on the machine hosting Faberon (a workstation, or a provisioned A100/H100 box).

Still tested against Karpathy's [autoresearch](https://github.com/karpathy/autoresearch) (5-minute `train.py`, `val_bpb` metric).

## In scope

- **Console package.** `packages/console/`, a Pi extension in TypeScript, sibling to `packages/control-plane/`. It talks to the control plane over the v0 HTTP contract with the bearer token from the environment. The extension exposes each v0 operation as a Pi tool (typed parameters, validated against the contract) plus a matching slash command; the drafter and live status build on that tool layer. It reasons conversationally, but every write is a human-initiated API call. The console proposes; the brain decides. The console versions independently of the control plane and ships its first release as `console-v0.1.0`, speaking API v0; it is distributed as a Pi package from the repo (`pi install git:github.com/sevren-ai/faberon@console-v0.1.0`), so users do not clone or build it. It is developed and tested against Pi `1.0.0` (`@earendil-works/pi-coding-agent`); the extension API we use (`registerTool`, `registerCommand`, `ctx.ui` widgets, packages) is 1.0.0 surface, and we pin to `^1.0.0` while Pi settles after its 1.0 refactor.
- **Drafter.** A conversational intake mode, hosted in the console, that interviews the human and drafts a `ResearchPlan`. It is a mode layered on the tool layer, not a standalone feature: it ends by submitting the reviewed plan through the same `create` path as a hand-written one. The drafter has no autonomous authority: its only output is a plan the human reviews and submits through `POST /v0/campaigns`. Control-plane validation stays the sole acceptance gate.
- **Idea injection.** `POST /v0/campaigns/{id}/ideas` wraps `DBOS.send`: the idea lands in the ledger as `idea.injected` and the proposer weighs it at its next decision boundary. Advisory only in this release: the proposer reads ideas as context, nothing forces execution. The imperative config flag arrives with the approval-gate work.
- **Live status.** The console streams `GET /v0/campaigns/{id}/events` (SSE) and renders the ledger live: proposals, completions, judgments, budget burn.
- **`experiment.designing` event.** The proposer's LLM call takes minutes and the ledger is silent meanwhile, which reads like a hang when watching the raw stream. The campaign loop records `experiment.designing` before the LLM call and `experiment.proposed` after, so the stream shows the wait.
- **`faberon` CLI.** Typer, same type-annotation style as the FastAPI/Pydantic stack. Flat verbs: `faberon serve`, `faberon list`, `faberon show <id>`, `faberon events <id>`, `faberon cancel <id>`, plus campaign creation and follow-up (below). The CLI reads the token and base URL from the environment (`FABERON_API_TOKEN`, `FABERON_API_URL`). The CLI is a thin client of the v0 write surface with no LLM in it.
- **Schema additions in the quarantined module:** `experiment.designing` and `idea.injected` event types.
- **Campaign creation from the CLI.** A `create` command submits a human-authored plan (file or flags) through `POST /v0/campaigns`. This closes the gap where plan submission alone still needed `curl`; it serves hand-written plans and plans copied out of a drafter session alike.
- **Succession from the best kept commit.** `POST /v0/campaigns` accepts an optional `predecessor` campaign id. The control plane derives the predecessor's best kept commit from its ledger (the `sha` of the last `experiment.judged` with `judgment=keep`) and its best kept metric, rejects a predecessor that is still active, and starts the new campaign's working tree at that commit. The new campaign's `campaign.created` payload records `predecessor: {campaign_id, sha}`.
- **Mechanical follow-up.** A `follow-up` command (CLI, and a console action on a finished campaign) derives the follow-up without an LLM: the predecessor's plan with fresh budget and `max_experiments` given explicitly, the baseline seeded from the predecessor's best kept metric, `predecessor` set, submitted through the same create path. This is the one-step form of the v0.2.1 re-seed recovery.
- **Drafter-assisted follow-up.** When the plan should change (new goal, revised stop conditions, a pivot informed by what was tried), the drafter starts from the finished campaign instead of a blank interview: it pre-fills the plan, summarizes what was tried from the event stream, and iterates with the human before submit. Same `predecessor` field underneath; control-plane validation stays the sole acceptance gate.
- **Local executor.** A new executor behind the existing `submit`/`status`/`cancel` interface runs the training script as a subprocess on the machine hosting Faberon. It serves users without a Slurm cluster. It covers the output-file convention the metric command reads, restart-safe submission idempotency without an external job registry (pid records on disk), and walltime enforcement without Slurm. An env switch selects it next to `create_app_slurm()`.
- Every job's stdout/stderr log is written to `{repo}/.faberon/{job_id}.out`, derived from the campaign's target repo (not from global config), and the metric command reads that file. The local executor's state dir holds only its pid records, never logs.
- **Workstation runbook.** A runbook for running Faberon on a single machine with the local executor. Postgres setup and restart stay manual (the `scripts/db/` scripts) until the lifecycle question settles; see [roadmap.md](roadmap.md).
- Console and CLI documented in the README and the cluster runbook.

## Out of scope

Planned for later releases: see [roadmap.md](roadmap.md). Speculative ideas: see [future.md](future.md).

- Parallel experiments (worktrees, DBOS queue): v0.4.0.
- Judgment quality (confidence measure, non-regression, constraint gates), the notes file, approval gates and the `POST /v0/approvals/{id}` write path: v0.5.0. The console in this release has no approvals to act on, because no actions are gated yet.

## v0.3.0 limitations

- **Drafter plan quality.** The drafter drafts; the human reviews and edits before submitting. No autonomous plan acceptance.
- **Hand-maintained contract types.** The console's `types.ts` mirrors the Pydantic models by hand while the v0 contract is still moving. Once it settles, the types are generated from the control plane's OpenAPI spec; planned for v0.4.0 (see [roadmap.md](roadmap.md)).
- **Idea timing.** An injected idea is visible to the proposer at its next decision boundary. An idea injected mid-experiment does not interrupt the in-flight job.
- **Console errors.** The console surfaces API errors as-is. No retry or offline queue.
- **No database schema migration.** The `events` table's `justification` column is renamed to `reason`, and the `campaigns` table's `command` column is folded into the plan. Faberon has no migration mechanism yet. Upgrading to v0.3.0 requires recreating the database (`scripts/db/drop-faberon-db.sh`, then `scripts/db/create-faberon-db.sh`); existing campaign and ledger data is discarded. Proper schema versioning is planned for a later release (see [roadmap.md](roadmap.md)).
- **A follow-up is a new campaign.** It does not continue the old workflow, budget, or experiment count. It is a fresh campaign whose plan and starting commit derive from its predecessor. Recovery of a still-pending workflow stays with `POST /v0/campaigns/{id}/resume` and is unchanged.
- **Mechanical follow-up needs explicit limits.** The follow-up command does not guess a budget: `budget_gpu_hours` and `max_experiments` are required inputs, since the predecessor's were consumed. The drafter-assisted path proposes them in conversation instead.
- **Local executor has no isolation or queueing.** Runs execute as subprocesses on the host machine, one at a time. A crashed or untracked process is cleaned up through its pid record; there is no cgroup, container, or node-level isolation, and no GPU allocation logic. Parallel local runs arrive with the queue work in v0.4.0.

## Exit test

On the login node, with the control plane running:

- Draft a plan through the console's drafter, review it, submit it. The campaign starts.
- Watch the campaign live through the CLI: `experiment.designing` appears while the proposer thinks, proposals, completions, and judgments stream in, budget burn updates.
- Inject an idea mid-campaign. It lands in the ledger as `idea.injected` and the next proposal reflects it.
- Cancel the campaign from the console. The loop stops at its next decision boundary with `campaign.ended` naming `cancelled`.
- The same four operations work through the `faberon` CLI with no `curl` and no hand-written URLs.
- Submit a hand-written plan through the CLI's create command. The campaign starts; no `curl` involved.
- Let a campaign end, then run the mechanical follow-up with explicit budget and experiment limits. The follow-up starts from the predecessor's best kept commit, its `campaign.created` event names the predecessor, and its first judgment compares against the seeded baseline.
- Draft a follow-up through the drafter instead. The plan arrives pre-filled, the summary matches the ledger, and the human edits before submitting.
- On a workstation with no Slurm, select the local executor through the env switch and run a short campaign end to end. The training script runs as a local subprocess, the metric command reads its output file, judgments and budget burn land in the ledger.
- With the local executor selected, kill the control plane while an experiment runs and restart it. The workflow resumes, the in-flight run is detected through its pid record, and no duplicate experiment is submitted.
- With the local executor selected, give an experiment a walltime it will exceed. The executor kills the subprocess at the limit and the campaign records the outcome like a Slurm timeout.
