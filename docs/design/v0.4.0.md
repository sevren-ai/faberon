# Design Document: Faberon v0.4.0 (security)

**Status:** draft (design review last updated 2026-10-06).
This doc describes what v0.4.0 should ship and is frozen afterwards.

## Goal

Reduce what a compromised or careless actor can do with Faberon. Three attack surfaces, one per threat model: the LLM writes code that runs on a cluster, the API token holder controls arbitrary commands, and the local executor runs with the brain user's full privileges. Today none of these are meaningfully contained. This release hardens all three without changing the campaign loop's scope.

## Threat models

Three distinct adversaries, addressed separately:

1. **The LLM is untrusted.** The proposer writes `target_file` contents that the cluster executes. A misaligned or manipulated model could write destructive, exfiltrating, or resource-abusing code.
2. **The API token can leak.** Anyone with `FABERON_API_TOKEN` gets cluster code execution and, via the local executor, login-node code execution. The worry is token theft on a shared login node or an over-broad API.
3. **Defense in depth.** Even a trusted operator can fat-finger a plan, and a compromised dependency in the FastAPI/DBOS/Pydantic AI stack should have bounded blast radius.

## In scope

- **Job sandboxing.** Run every experiment job in a container (Apptainer on Slurm clusters, or a rootless runtime for the local executor) with no network, a read-only mount of the experiment repo, and a writable scratch dir for outputs. Slurm already cgroups CPU/GPU/memory; the container adds filesystem and network confinement. The only mitigation that does not trust the LLM's code.
- **Constrain `command` to a validated shape.** Replace the free-form `command` string with a structured form: an allowlisted interpreter (`python`, `python3`, `uv run`) plus a script path that must resolve inside the campaign's `repo_path`. The brain validates the shape and the path before accepting the plan. This turns "arbitrary code execution" into "run a script from the checked-out experiment repo," which matches the design intent. Breaking change to the v0 contract.
- **AST policy on proposals.** Extend the proposer's output validator beyond `ast.parse`: reject proposals that import or call a denylist (`subprocess`, `os.system`, `socket`, `ctypes`, `shutil.rmtree` outside the repo, and similar). A filter, not a guarantee; it catches accidents and low-effort misuse, not a determined adversary. Documented as such.
- **Token hardening.** Replace the single static bearer token with per-client tokens minted by the operator, or bind the API to a Unix domain socket with filesystem permissions doing the auth. The design doc already flags the shared login node as the reason the token exists; this closes it.
- **Local executor hardening.** The local executor runs jobs as the brain user with no resource limits and the full environment. Add resource limits (CPU, memory, walltime already exists), a confined working directory, and a scrubbed environment (no SSH keys, no push-capable git credentials).
- **Cluster-side guardrails.** Document and, where possible, enforce Slurm account QoS limits (max GPUs, max walltime, max concurrent jobs) so a fully compromised control plane can only burn a bounded, auditable slice of the allocation.
- **Confine `repo_path` to an allowlist root.** Today a token holder can point a campaign at any path the brain's user can write. An env var such as `FABERON_REPO_ROOT` that `repo_path` must resolve under contains both accidents and token misuse. The brain rejects a campaign whose `repo_path` escapes the root.

## Out of scope

Planned for later releases: see [roadmap.md](roadmap.md). Speculative ideas: see [future.md](future.md).

- Parallel experiments (worktrees, DBOS queue)
- Judgment quality (confidence measure, non-regression, constraint gates), the notes file, approval gates and the `POST /v0/approvals/{id}` write path
- Contract tooling (OpenAPI goldens, generated TypeScript types)

## v0.4.0 limitations

- **The AST policy is not a sandbox.** It is a denylist filter on the proposal text. A model that wants to evade it can. The container is the real boundary.
- **The `command` shape change breaks v0 clients.** The chat interface and any hand-written plan JSON must be updated. v0 is explicitly unstable; this is the cost of learning.
- **Token migration is operator work.** Existing deployments must mint new tokens or switch to the Unix socket. The old static token stops working at upgrade.

## Exit test

On the login node, with Faberon running:

- Submit a plan whose `command` is a bare string. It is rejected with a clear error naming the new structured shape.
- Submit a plan whose `command` names a script outside the repo. It is rejected.
- Submit a plan whose `command` uses an interpreter not on the allowlist. It is rejected.
- Let the proposer write code that imports `subprocess`. The validator rejects it and the proposer retries.
- Inspect the Slurm job: it runs inside a container, cannot reach the network, and cannot write outside its scratch dir.
- Connect to the API with the old static token. It is rejected. Connect with a per-client token or over the Unix socket. It works.
- Run a local-executor job: it has resource limits, a confined working directory, and no SSH keys in its environment.
